函式呼叫與 Stack 逐步圖解

一條 call 做了什麼、ret 怎麼知道回哪裡、frame 怎麼疊起來又拆掉。用真實位址一步一步走，順便看為什麼 call 的瞬間 rsp 必須是 16 的倍數。

只有兩個指標在動

rip 指向下一條要執行的指令，rsp 指向 stack 的頂端。Stack 往低位址長，所以 push 是先把 rsp 減 8 再寫入，pop 是先讀出再把 rsp 加 8。

call 等於「push 下一條指令的位址，然後 jmp」。ret 等於「pop 到 rip」。這就是全部的硬體機制。其他所有東西，包括 16 bytes 對齊、callee-saved、frame pointer，都是編譯器在這兩條指令之上的約定。下面的 stepper 會把 call 和 ret 各拆成兩個半步，讓 rsp 和 rip 的變化分開看。

為什麼是 16 的倍數

規則原文：執行 call 的瞬間 rsp 必須是 16 的倍數。因為 call 一定推 8 bytes，所以每個函式進入時 rsp 一定餘 8。編譯器靠這個保證在編譯期就算出 sub rsp, 24 這種常數，讓 stack 上的 16 bytes 物件(xmm spill、long double、__int128)不需要執行期對齊。

硬體不檢查這條規則，違反的後果出現在被呼叫的那一方：它內部用 movaps 存取 stack 時位址對不齊，直接 fault。在第一個範例勾選「拿掉 push rbx」就能看到 printf 內部炸掉。這也是手寫組語或 JIT 最常見的 crash 來源。

反過來說，任何要 call 別人的函式，進入後都得讓 rsp 再少 8 的奇數倍。大多數函式本來就有 push 的需求，順便就對齊了；真的沒有需求的函式會多一條純補位的 push，或是被優化成 jmp 的 tail call 而完全省掉，見 tail call 那組範例。

遞迴到底能多深

每一層呼叫都在 stack 上留下一個 frame，直到撞上 stack 末端的 guard page。Linux 主執行緒的 stack 預設 8 MiB,frame 大小由編譯器決定。拖動深度看 rsp 往下走到哪裡。

返回位址放在 stack 上的代價

返回位址和區域變數住在同一塊記憶體，只隔幾個 bytes。一個 char buf[8] 配上不檢查長度的 strcpy，多寫幾個字就會蓋到 saved rbx，再多幾個就蓋到返回位址，ret 之後 rip 跳到攻擊者決定的地方。這是 1988 年 Morris worm 到今天所有 stack smashing 的原型。在最後一組範例裡拖動字串長度，再勾選 stack protector 看 canary 怎麼擋。

結語

硬體只提供兩個動作：call 把返回位址推進 stack 再跳走，ret 把它彈回 rip。Frame、16 bytes 對齊、callee-saved 都是編譯器疊在這兩個動作上的約定，硬體不檢查，所以違反的後果不在違反的那一行，而在被呼叫的函式裡炸開。返回位址和區域變數住在同一塊記憶體，這是 stack smashing 能成立的全部原因。

哪個暫存器放參數、哪些要保存，在暫存器地圖那一頁；把同一個問題拿到 ARM 和 RISC-V 上比，在 ISA 比較的呼叫慣例那一篇。

這一頁只走 SysV AMD64，位址是示意的，frame 大小也是為了畫圖挑的；Win64 的 shadow space、exception unwinding、32 位元的 cdecl 和硬體 shadow stack 列在下面的「這一頁沒講的」裡，沒有展開。

這一頁沒講的
  • Win64 的差異：同樣要求 call 時 16 對齊，另外 caller 要多留 32 bytes shadow space。參數暫存器的差異見暫存器地圖。
  • Exception unwinding、setjmp/longjmp：一次跳過多層 frame 的機制，靠 .eh_frame 表而不是 rbp 鏈。
  • 32 位元的 cdecl：參數全部走 stack,caller 負責清理。x86-64 已經不用。
  • Shadow stack / CET:Intel 2020 年起的硬體機制，把返回位址另外存一份在 CPU 保護的區域，ret 時比對，專門對付這頁最後一個範例。
