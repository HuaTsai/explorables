← DDS 與 ROS 2 底層

ROS 2 疊在 DDS 上的那一層

在 ROS 2 裡發一個 /turtle1/cmd_vel，DDS 上看到的 topic 叫 rt/turtle1/cmd_vel，型別叫 geometry_msgs::msg::dds_::Twist_。這一頁看 ROS 2 在 DDS 上面疊了什麼、名稱和 QoS 怎麼對應，最後輸入一個 ROS 名稱，看它到了 DDS 長什麼樣子。

為什麼不直接用 DDS

ROS 2 選 DDS 當底層，是看上它現成的自動探索、QoS 和可靠傳輸。但它沒有讓使用者直接寫 DDS，而是自己疊了一層，原因有四個：

  • 可以換實作。各家 DDS 的 API、程式產生器、設定檔都不一樣。ROS 2 在中間放了一層統一的介面，換實作只要改一個環境變數，程式不用動。
  • DDS 的 API 太大。ROS 只留下使用者需要的概念：node、publisher、subscription，以及幾組現成的 QoS 組合。
  • 機器人需要、DDS 沒有的東西。service、action、parameter、模擬時間、executor、launch，都是 ROS 自己做的。
  • 甚至可以不用 DDS。介面是抽象的，所以底層也能換成別的協定，例如 Zenoh。

訊息的程式也分兩種做法。靜態的做法是在 build 時替每個訊息產生專用的序列化程式，例如 Fast DDS 用的 rosidl_typesupport_fastrtps_cpp。動態的做法是只產生一份「有哪些欄位」的描述（rosidl_typesupport_introspection_cpp），執行時照著描述處理。動態的和實作無關，但比較慢。Cyclone 的 rmw 用的是動態的；Fast DDS 兩種都有，rmw_fastrtps_cpp 是靜態的，rmw_fastrtps_dynamic_cpp 是動態的。不管哪一種，使用者寫的程式都只看得到 ROS 的訊息 class。

名稱怎麼對應

ROS 的名稱有 namespace、有斜線，DDS 的 topic 名稱只是一個字串。ROS 2 在 rmw 這一層把兩者對起來，規則是：

  1. topic：在完整名稱前面加 rt。/turtle1/cmd_vel 變成 rt/turtle1/cmd_vel。
  2. service：拆成兩個 DDS topic。request 是 rq + 名稱 + Request，reply 是 rr + 名稱 + Reply，中間不加分隔符號。
  3. 型別：pkg/msg/Type 變成 pkg::msg::dds_::Type_。service 的型別拆成 Type_Request 和 Type_Response 兩個，各自照同樣的規則轉換。
  4. 反方向：工具列出 topic 時，把有 rt/ 的名字還原回 ROS 名稱，沒有前綴的直接略過。

設計文件還保留了 rs、rp、ra（service、parameter、action），但現在的實作只用到 rt、rq、rr。parameter 和 action 是用 service 和 topic 組出來的，所以線上也只會看到這三種前綴。publisher 的 QoS 裡有一個 avoid_ros_namespace_conventions，設成 true 就不加前綴，用來和非 ROS 的 DDS 程式溝通。

QoS profile

ROS 2 預先定義了幾組 QoS 組合，最常用的三組（來自 rmw/qos_profiles.h）：

profilehistoryreliabilitydurability典型用途
defaultKEEP_LAST 10RELIABLEVOLATILE一般 topic
sensor dataKEEP_LAST 5BEST_EFFORTVOLATILE雷射、相機這種高頻資料，掉幾筆沒關係、要最新的
services defaultKEEP_LAST 10RELIABLEVOLATILEservice 的 request 和 reply

相容規則就是 DDS 的 RxO：subscription 要求的不能比 publisher 提供的嚴格。ROS 2 文件列出的不相容組合有：reliability 是 best effort 的 publisher 配 reliable 的 subscription；durability 是 volatile 的 publisher 配 transient local 的 subscription；以及 deadline、liveliness、lease duration 的對應組合。最常見的狀況是驅動程式用 sensor data 發 /scan，訂閱的一方卻用 default。這時 publisher 端會印出：

New subscription discovered on topic '/scan', requesting incompatible QoS.
No messages will be sent to it. Last incompatible policy: RELIABILITY

反過來，subscription 用 sensor data 去收 default 的 publisher 是可以的：提供 RELIABLE、只要求 BEST_EFFORT，提供的比要求的高。第一篇的 workbench 可以直接跑這兩種情況。

看不見的部分

一個程式一個 participant。早期的 ROS 2 是一個 node 一個 DDS participant；後來改成一個 context（通常就是一個程式）只有一個 participant，因為 participant 是探索流量的主要來源。但這樣一來，DDS 只知道「這個 participant 有哪些 writer、reader」，不知道它們屬於哪個 node。ROS 2 的解法是再開一個 topic，叫 ros_discovery_info：每個 participant 在上面公告「我底下有哪些 node，每個 node 有哪些 reader、writer」，用 transient local，晚加入的程式也拿得到。它是用 avoid_ros_namespace_conventions 建的，沒有 rt/ 前綴，所以 ros2 topic list 看不到它。

型別雜湊。從 Iron 開始，每個訊息型別在 build 時會算出一個雜湊（RIHS），探索時放在 DDS 的 USER_DATA 裡傳出去，格式是 typehash=RIHS01_…;，ros2 topic info -v 看得到。這部分的規格寫在 REP-2016，目前仍是草稿，還沒有正式發布。不過目前看到的實作只是把它帶上、顯示出來，並沒有因為雜湊不同就拒絕配對。rclcpp 有一個「incompatible type」事件，但它是由 DDS 的 INCONSISTENT_TOPIC 狀態觸發的，底下的 DDS 不支援這個狀態時就不會發生。所以「型別名稱一樣、內容不一樣」這個坑，在 ROS 2 裡還是要靠自己管理。

結語

ROS 2 在 DDS 上疊的那一層，核心是 rmw：上面的 rcl、rclcpp 只認得 rmw 的介面，下面每一種 DDS 各有一個 rmw 實作，用 RMW_IMPLEMENTATION 切換。名稱的對應是固定規則：topic 加 rt，service 拆成 rq…Request 和 rr…Reply，型別變成 pkg::msg::dds_::Type_。不管換哪一家 DDS，這些名字都一樣，所以不同實作的 ROS 2 程式可以互通，非 ROS 的 DDS 程式只要照同樣的規則取名，也能被 ROS 2 看到。
