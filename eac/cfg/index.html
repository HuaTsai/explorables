CFG 從線性 IR 建控制流程圖

編譯器中段看到的是一串線性的指令。要做分析和最佳化，得先知道控制流會怎麼走：哪幾條指令一定連著執行、從哪裡能跳到哪裡。這一頁把 Engineering a Compiler 第四章建 CFG 的兩段虛擬碼一步步跑給你看：FindLeaders 找出每個 basic block 的第一條指令，BuildGraph 找出每個 block 的最後一條並連上邊。可以換範例，也可以自己改 ILOC 程式碼。

線性 IR 缺了什麼

ILOC 是書上用的線性 IR：一條指令一行，label 標在指令前面。線性 IR 好產生、好存，但「第 5 條執行完接著跑第 6 條嗎？」這件事它沒有明寫。要回答這個問題，先把指令切成 basic block：一段最長的連續指令，只能從第一條進來，只能從最後一條離開。所以 block 中間沒有 label（沒有人能跳進來），也沒有 branch（不會中途跳走）。

控制流程圖（CFG）的節點是 block，邊是可能的控制轉移。block 的第一條指令叫 leader。找到所有 leader，block 就切好了；再看每個 block 最後一條指令往哪跳，邊就連好了。這正好就是兩段演算法。

ILOC 的三種控制流指令

指令意思建圖時知道目標嗎
cbr rk → l1, l2條件分支：rk 為真跳 l1，否則跳 l2。兩個目標都明寫。知道，兩個
jumpI → l1無條件跳到 label l1。知道，一個
jump → r1跳到 r1 裡存的位址。不知道，可能是任何 label

關鍵是 ILOC 沒有 fall-through：cbr 不會「不跳就繼續往下」，兩邊都是明寫的跳轉。這個設計直接決定了 FindLeaders 長什麼樣：一條指令能被跳到，當且僅當它有 label。所以「找 leader」就是「找 label」，不用再看前一條是不是 branch。大多數真實的組語都有 fall-through，到時候演算法要多一個 case，後面會講。

兩段演算法

書上的虛擬碼照抄如下。n 是指令數，opi 是第 i 條指令。FindLeaders 掃一遍，把每個有 label 的指令編號填進 Leader 陣列，順手建節點。BuildGraph 對每個 leader 往下掃到下一個 leader 之前，記下 Last，再看 block 最後一條是什麼，決定加哪些邊。

FindLeaders()
  next ← 1
  Leader[next++] ← 1
  create a CFG node for l1
  for i ← 2 to n do
    if opi has a label li then
      Leader[next++] ← i
      create a CFG node for li
  MaxStmt ← next − 1

第一條指令無條件是 leader，之後每一條有 label 的指令都是。MaxStmt 是 block 的個數。

BuildGraph()
  for i ← 1 to MaxStmt do
    j ← Leader[i] + 1
    while (j ≤ n and opj ∉ Leader) do
      j ← j + 1
    j ← j − 1
    Last[i] ← j
    if opj is "cbr rk → l1, l2" then
      add edge from j to node for l1
      add edge from j to node for l2
    else if opj is "jumpI → l1" then
      add edge from j to node for l1
    else if opj is "jump → r1" then
      add edges from j to all labeled statements

while 往下掃到下一個 leader 停下，退一格就是這個 block 的最後一條。邊只看最後一條。

虛擬碼裡最容易讀錯的四行

    
    
      
  • opj ∉ Leader 是在問編號，不是在看指令。它的意思是「j 這個編號不在 Leader 陣列裡」。實作上要有 O(1) 的成員測試，例如一個 n 位的 bit vector；拿陣列線性搜尋，BuildGraph 就不再是線性時間。
    • 
      
  • j ← j − 1 是因為 while 多走了一步。迴圈停下來時 j 停在下一個 leader（或 n + 1），那條不屬於這個 block，退一格才是最後一條。
    • 
      
  • 其實有更短的寫法。Leader 是遞增填入的，所以 Last[i] 就是 Leader[i + 1] − 1，最後一個 block 則是 n。書上寫成掃描，是把「block 一路延伸到下一個 leader 之前」講白。整個 BuildGraph 的 while 加起來每條指令只看一次，還是 O(n)。
    • 
      
  • 邊的來源是 block，不是指令。「add edge from j」裡的 j 是 block i 的最後一條，圖上畫的是 Bi 出去的邊。目標 l1 的節點，就是 leader 帶著那個 label 的 block。

書上接著講的複雜情況

    
    
      
  • 目標在暫存器裡（ambiguous jump）。jump → r 編譯時不知道要跳去哪，演算法保守地連到每一個有 label 的 block。邊太多會讓後面的資料流分析結果變鈍。書上提到可以在 jump 後面用 tbl 這類 pseudo-op 列出可能的目標，建圖時只連那幾個。範例「jump → r」可以看到保守做法長什麼樣。
    • 
      
  • IR 有 fall-through。如果條件分支「不跳就往下走」，branch 的下一條也是 leader，而且要多加一條到它的邊。FindLeaders 和 BuildGraph 各要多一個 case。
    • 
      
  • branch 後面沒 label 的指令。在 ILOC 裡它不可達。演算法不會把它當 leader，於是它被吸進前一個 block，前一個 block 的最後一條不再是那個 branch，邊就丟了。範例「branch 後面沒 label」示範這個情況。實務上要在建圖前先刪掉這種死碼，或把它當 leader，讓它變成一個沒有入邊的節點。
    • 
      
  • 沒有人跳到的 label。仍然是 leader、仍然建節點，只是沒有入邊，在 CFG 裡不可達。不過 jump → r 的保守做法會給它一條入邊。
    • 
      
  • 程序呼叫。這兩段演算法沒把呼叫當成 branch。有些編譯器選擇在呼叫處切開 block，方便處理跨程序的效應或例外。

結語

    
找 leader 就是在找「能從別處進來的點」：ILOC 沒有 fall-through，所以等於找 label；有 fall-through 的 IR 要再算上每條 branch 的下一條。block 的結尾由下一個 leader 決定，邊由 block 最後一條指令決定，這是兩件事，演算法也分成兩段。整個做法的正確性靠 IR 的性質撐著，換一個 IR，先問「哪些指令能被跳到」和「哪些指令會跳走」，再改這兩段。

    
有了 CFG，接下來的最佳化都在它上面走。同一本書第八章的 區域值編號只看一個 block 裡面，是最先遇到的 pass；樹高平衡也是 block 內的變換。跨 block 的分析（dominator、資料流分析）需要的就是這張圖的節點和邊，書上第九章開始講。

    
很多編譯器會加 entry 和 exit 兩個虛擬節點代表程序的進入和離開，這裡只有 block。節點和邊的資料結構、重複邊怎麼去重，書上這一段沒講，這一頁重複的邊只畫一條。建完圖之後把沒有入邊的 block 拿掉是另一個 pass。例外、間接呼叫、多目標的 jump table 這些控制轉移，這裡只用 jump → r 一種代表；算術、載入、儲存、比較都當普通指令，內容不影響建圖。
