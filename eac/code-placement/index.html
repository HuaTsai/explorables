程式碼放置：把 hot path 排成 fall-through

CFG 那一頁把程式切成 block，順序就是原始碼的順序。但 block 最後要排回一條線放進記憶體，誰接在誰後面是編譯器可以選的。分支如果跳到緊接在後面的那個 block，就是 fall-through，不用真的跳；跳到別的地方才要一條跳躍，會打斷指令的預取，也可能把常一起跑的兩段程式碼放到不同的 cache line。全局程式碼放置的目標就是讓最常走的那些邊變成 fall-through。Engineering a Compiler 8.6.2 的做法分兩段：先照邊的執行次數把 block 貪婪地串成鏈，再按優先序把鏈排成一列。這一頁照書上的兩段虛擬碼一步步跑，可以自己改邊和次數。

為什麼 block 的順序有關係

在 ILOC 裡一條分支把兩個目標都寫明，看不出哪一個比較便宜。真的機器不是這樣：block 結束時如果下一個要執行的 block 就排在正後方，那條跳躍可以省掉，或者至少是一條不會跳的分支；指令預取和 cache 都偏好直直往下走。所以同一張 CFG，不同的線性順序，執行時真的跳的次數不同。每個 block 只有一個正後方，所以最多只能把一條出邊變成 fall-through，其他的出邊一定要跳。

要知道哪些邊常走，需要每條邊的執行次數。這個數字可以來自 profile，也可以來自靜態估計，像是把迴圈的 back edge 當作走十次；演算法本身不在乎數字從哪裡來。書上在這一節旁邊有一段對照：資料流分析在編譯期用數學把所有可能的路徑都算進去，所以保守；profile 記的是某一組輸入的某一次執行，所以激進，它假設未來的執行會像這一次。兩種資訊在最佳化裡都有用，上一頁的 LiveOut 用前者，這一頁用後者。書上的例子直接把次數標在邊上，這一頁的輸入也是。

鏈、優先序和兩條規則

第一段演算法把 block 串成鏈。開始時每個 block 自己是一條退化鏈。接著把所有的邊照次數從高到低看一遍：邊 ⟨x, y⟩ 只有在 x 是它那條鏈的尾、y 是另一條鏈的頭時，才能把 y 那條鏈整個接到 x 後面。一旦接上，x → y 就注定會是 fall-through。這個條件是「每個 block 的正前方和正後方都只有一個位置」的直接結果：x 後面已經接了別人，就沒有位置給 y；y 前面已經有別人，x 就擠不進去。越熱的邊越早處理，位置先給它。

每條鏈還帶一個優先序。開始時是 E，也就是邊的總數，等於無限大。有一個計數器 P 從 0 起算，每處理一條邊就加一，所以 P 的值就是「這是第幾條被處理的邊」，數字越小代表這條邊越熱。接鏈時新鏈的優先序取兩條舊鏈和這條邊的最小值；接不上時，包含 y 的鏈也拿這條邊的序號去比，比較小就換成它。結果是：一條鏈的優先序等於「碰過它的最熱的那條邊」的序號。

第二段演算法把鏈排成一列。鏈的集合只是 block 上的一個偏序，要變成全序，書上用兩條啟發式規則：一條鏈裡的 block 照鏈的順序放，讓 hot path 成為 fall-through；鏈和鏈之間按優先序從低到高放。第二條用一個 worklist 實作：從入口所在的鏈開始，放完一條鏈，就把它指出去、還沒放的 block 所屬的鏈加進 worklist，每次取優先序最低的那條來放。

虛擬碼

書上分成兩段。第一段建鏈，第二段排版。中譯本的兩段虛擬碼分別是圖 8-17 和圖 8-19，第一個範例的 CFG 和每一步的鏈集合表是圖 8-18，第二個範例是同節末尾的「最終示例」。

E ← |edges|
for each block b do
  create a degenerate chain, d, for b
  priority(d) ← E
P ← 0
for each CFG edge ⟨x,y⟩, x ≠ y,
    in decreasing frequency order do
  if x is the tail of chain a and
     y is the head of chain b then
    t ← priority(a)
    append b onto a
    priority(a) ← min(t, priority(b), P++)
  else priority(b) ← min(priority(b), P++)

建鏈。P++ 是「先用現在的值，再加一」，所以每條邊拿到的序號就是它被處理的順序。else 那一行的 b 是包含 y 的鏈。

t ← chain headed by the CFG entry node
WorkList ← { (t, priority(t)) }
while (WorkList ≠ ∅) do
  remove a chain c of lowest priority from WorkList
  for each block x in c in chain order do
    place x at the end of the executable code
  for each block x in c do
    for each edge ⟨x,y⟩ where y is unplaced do
      t ← chain containing y
      if (t, priority(t)) ∉ WorkList then
        WorkList ← WorkList ∪ { (t, priority(t)) }

排版。放完一條鏈才掃它出去的邊，所以 worklist 裡永遠是「已經放好的程式碼有邊指過去」的鏈。

  • x ≠ y 把自己指自己的邊排除。一個 block 回到自己的 back edge 不管怎麼排版都是一條跳躍，對置放沒有影響，所以跳過。
  • else 那一行也會動優先序。接不上的邊沒有白費：包含 y 的鏈拿到這條邊的序號，如果比它原本的優先序小就換成它。這樣一條被很熱的邊指到、但接不上的鏈，排版時還是會早早被放，離跳過來的地方近一點。圖 8-18b 裡處理 ⟨B4, B3⟩ 那一步可以確認 b 是包含 y 的鏈：B3 所在的 ⟨B2, B3⟩ 優先序已經是 1，min(1, 2) 沒變，而 ⟨B4⟩ 維持 E。
  • 次數相同的邊，書上沒有規定順序。不同的順序會做出不同的鏈。這一頁在次數相同時照輸入列出的順序處理，所以調換兩行就能看到另一種結果。
  • 這一頁補了兩條書上沒寫的規則。如果 x 是鏈尾、y 是鏈頭、而且是同一條鏈，接上去鏈會變成一個圈，所以當作接不上；有迴圈的圖一定會碰到這個情況。另外，指向入口的邊也不接，因為入口必須是程式碼的第一個 block，不能排在別人後面。書上排版的第一行寫「以入口為頭的鏈」，隱含了入口一定是鏈頭；沒有第二條規則的話，一條指回入口的熱邊會把它接到別的 block 後面，第一行就找不到鏈了。
  • worklist 裡優先序相同時取先進來的。書上只說取最低的；這一頁用先進先出打平手，和 P 的序號一樣反映「先碰到的先放」。

次數相同時，順序不只一種

    
書上的例子有三條次數都是 5 的邊。照圖 8-18b 的順序，先處理 ⟨B2, B3⟩，B3 就接在 B2 後面，之後的 ⟨B4, B3⟩ 接不上，最後得到 ⟨B0, B1, B2, B3⟩ 和 ⟨B5, B4⟩。如果先處理 ⟨B4, B3⟩，就變成 ⟨B0, B1, B2⟩ 和 ⟨B5, B4, B3⟩，排版出來是 B0 B1 B2 B5 B4 B3。範例「先處理 ⟨B4, B3⟩」就是這個順序。書上說，只要次數的估計是對的，這兩種佈局沒有優劣之分：兩種都讓 20 次執行走在 fall-through 上，剩下 10 次要跳。「fall-through 承接的次數」是這一頁拿來比較佈局的方法，不是書上的：把相鄰的 block 兩兩看一遍，中間有邊的就把次數加起來。workbench 的最後一步會算。

    
貪婪法不保證找到最好的順序。找最好的線性順序本身是個難題，它包含了帶權重的 Hamiltonian path，所以實務上都是貪婪加啟發式。書上的說法是：就算鏈的處理順序不是最好的，排版演算法還是能做出不錯的結果。因為排版只看鏈和優先序，鏈怎麼切、優先序差多少，影響的只是哪幾條次要的邊要跳。這套「照邊的權重貪婪接鏈、再照優先序排鏈」的做法來自 Pettis 和 Hansen 1990 年的論文，GCC 的 bb-reorder 和 LLVM 的 MachineBlockPlacement 都是它的後代，只是多了對迴圈、block 大小和分支預測的考慮。

  


  

    
迴圈和入口

    
有迴圈的圖裡最熱的邊常常是 back edge。範例「迴圈裡有一條少走的分支」裡，⟨B5, B1⟩ 是第二熱的邊，而且 B5 是鏈尾、B1 是鏈頭，所以它被接上了：迴圈的最後一個 block 排在 header 前面，鏈變成 ⟨B5, B1, B2⟩。這沒有錯，一個迴圈每繞一圈至少要跳一次，演算法只是把那一次跳放在別的邊上。後來 ⟨B3, B5⟩ 的 B3 是這條鏈的尾、B5 是這條鏈的頭，接上去就成了圈，所以照這一頁補的規則當作接不上。最後少走的 B4 反而接到 B5 前面，整條鏈是 ⟨B4, B5, B1, B2, B3⟩：進迴圈要跳一次，每圈 B3 回 B5 跳一次，其他都是 fall-through。

    
入口 B0 在這個範例裡自己一條鏈，優先序一直是 E，因為沒有任何邊指向它。排版的第一行不看優先序，直接從入口的鏈開始，所以 E 不是問題；它只對排版中途才進 worklist 的鏈有意義。

  


  

    
次數從哪裡來，和為什麼不用每條邊都插樁

    
最直接的做法是在每條邊上插一個計數器。但計數有守恆：除了入口和出口，每個 block 進來的次數總和等於出去的次數總和，因為執行流進了一個 block 一定會從某條出邊離開。圖 8-18a 裡 B4 進來 2 + 3，出去 5；B0 進來 10，出去 7 + 3。所以只要量了一部分的邊，其他的可以用守恆算回來。把出口接一條虛擬的邊回入口，整張圖的次數就是一個處處守恆的流，這時任何一棵生成樹上的邊都可以不量，由樹外的邊推回來；要插樁的只有樹外的邊，而且挑權重最大的生成樹可以讓插在熱邊上的計數器最少。這是 8.6 節末復習題 2 問的東西。Knuth 和 Stevenson 1973 年提出用生成樹減少測量點，Ball 和 Larus 1994 年做成了挑最大權重生成樹的版本，gcov 和 LLVM 的 instrumentation profiling 到現在還是這麼做。

  


  

    
結語

    
程式碼放置把 CFG 排回一條線，目標是讓最常走的邊變成 fall-through。每個 block 的正後方只有一個位置，所以演算法照次數從高到低分配：x 是鏈尾、y 是鏈頭才能接，接上的邊注定是 fall-through。優先序記的是碰過這條鏈的最熱的邊是第幾條，排版時從入口的鏈開始，用 worklist 每次放優先序最低的鏈，再把它指出去的鏈加進來。次數相同的邊處理順序不同，鏈就不同，但只要次數是對的，結果差不多一樣好。

    
這是書上第八章四個例子裡唯一用 profile 而不是資料流分析的。第九章接著把 LiveOut 推廣成資料流框架，並且講 dominator；程式碼放置本身在真的編譯器裡還要處理迴圈對齊、把冷的 block 搬到函式的另一頭、以及看分支預測器的習慣。它建立在 CFG 的 block 和邊上，和 LiveOut 是同一節的兩個小節。同樣的想法放大到整個程式，就是 8.7.2 的過程放置：在 call graph 上縮邊，讓常互相呼叫的過程放得近。

    
這一頁的模型把 block 當成沒有大小的點，只看邊的次數。真的機器還在乎 block 的位元組數和 cache line 對齊、分支預測器對前向和後向分支的預設猜測、跳躍能跳多遠；排好之後每個 block 末尾的分支也要重寫，fall-through 那邊的跳躍要拿掉，必要時把條件反過來。這些都不在書上這一節，也不在 workbench 裡。
