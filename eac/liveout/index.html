LiveOut 活躍變數分析：迭代到不動點

SVN 碰到 join point 就從空表開始，因為它不敢對「從哪一邊來」做任何假設。全局最佳化要對整張 CFG 推理，就得有辦法把每一條路徑都算進來。Engineering a Compiler 第八章用活躍變數當第一個例子：對每個 block 算出 LiveOut(b)，也就是離開 b 時哪些變數的值之後還會被讀到。做法是對整張圖寫一組方程式，從空集合開始反覆代入，直到沒有東西再變。這一頁照書上的兩段虛擬碼一步步跑，最後用 LiveOut 找出可能沒初始化就被用到的變數。

區域方法到此為止

LVN 看一個 block，SVN 看一條路徑，兩者共同的限制是碰到有多個前驅的 block 就得把知道的事全部丟掉。全局最佳化不沿著這條路繼續走：它不去模擬執行順序，而是對 CFG 的每個節點列一條方程式，描述「這個 block 的事實」和「它鄰居的事實」之間的關係，再把整組方程式解出來。這一類分析叫資料流分析，書上第九章整章講它，8.6 節先用最經典的一個問題示範。

問題是這樣：變數 v 在程式點 p 活躍，若且唯若從 p 出發存在一條路徑，在重新給 v 賦值之前先讀了 v 的值。這是一個「看未來」的性質，要考慮 p 之後所有可能的執行路徑，所以 block 內的方法做不到。編譯器很多地方要用這個資訊：暫存器分配時不活躍的值不必留在暫存器裡，存到記憶體之後再也沒人讀的 store 可以刪掉，建 SSA 時只有活躍的變數需要 φ 函數。這一節的目標是其中最直接的一個，找出可能還沒初始化就被用到的變數。

三個集合和一條方程式

先把「活躍」的定義搬到 block 的粒度。每個 block b 有兩個只看自己就能算出來的集合，和一個要看鄰居的集合：

  • UEVar(b)：在 b 裡被讀、而且那次讀之前 b 自己沒有先給它賦值的變數。這些變數的值是從 b 的入口帶進來的，書上叫 upward-exposed。
  • VarKill(b)：在 b 裡被賦值的變數。不管進 b 的時候帶著什麼值，離開 b 時這些名字的值一定已經被 b 蓋掉。
  • LiveOut(b)：離開 b 的那一刻活躍的變數。這是要算的東西。

離開 n 之後下一步一定是進入某個後繼 m。變數 v 離開 n 時活著，只有兩種可能：m 自己在賦值之前就讀了 v，也就是 v ∈ UEVar(m)；或者 v 穿過 m 沒有被改（v ∉ VarKill(m)），而且離開 m 的時候還活著（v ∈ LiveOut(m)）。n 有好幾個後繼時走哪一條都有可能，「存在一條路徑」對應到聯集。寫成方程式：

\[ \mathrm{LiveOut}(n) = \bigcup_{m \in \mathrm{succ}(n)} \Big( \mathrm{UEVar}(m) \cup \big( \mathrm{LiveOut}(m) \cap \overline{\mathrm{VarKill}(m)} \big) \Big) \]

上面那條橫線是補集，\(\mathrm{LiveOut}(m) \cap \overline{\mathrm{VarKill}(m)}\) 就是 LiveOut(m) 扣掉 VarKill(m)，這一頁的 workbench 寫成 LiveOut(m) ∖ VarKill(m)。沒有後繼的出口 block，右邊是空的聯集，LiveOut 是 ∅：離開程式之後什麼都不會再被讀。

這條方程式有兩個特點決定了解法。第一，資訊從後繼流向前驅，和執行方向相反，所以這是一個backward 問題。第二，有迴圈的時候方程式會互相依賴：書上例子裡 B1 的 LiveOut 要看 B3，B3 的又要看 B1，沒辦法排一個順序一條一條算完，只能先猜一組值，反覆代入，直到每一條方程式都同時成立。這種「代入到不再改變」的點叫不動點。

虛擬碼

書上分成兩段。第一段對每個 block 掃一遍運算，收集 UEVar 和 VarKill；第二段把所有 LiveOut 設成空集合，然後一圈一圈重算，直到某一圈沒有任何集合改變。中譯本把兩段虛擬碼放在圖 8-15，範例的 CFG、初始集合和每一圈的 LiveOut 表是圖 8-16。書上 B1 的內容只寫 (test on i)，表示一個讀 i 的分支條件，這一頁的輸入格式照抄這個寫法。

// each block has k operations
// of the form "x ← y op z"
for each block b do
  // Initialize the sets for b
  UEVar(b) ← ∅
  VarKill(b) ← ∅
  for i ← 1 to k do
    if y ∉ VarKill(b) then
      add y to UEVar(b)
    if z ∉ VarKill(b) then
      add z to UEVar(b)
    add x to VarKill(b)

收集初始資訊。掃到第 i 條運算時，VarKill(b) 裡是前 i − 1 條賦值過的名字，所以「y ∉ VarKill(b)」問的是「y 的值是不是從 block 外面帶進來的」。

// assume the CFG has N blocks
// numbered 0 to N-1
for i ← 0 to N-1 do
  LiveOut(i) ← ∅
changed ← true
while (changed) do
  changed ← false
  for i ← 0 to N-1 do
    recompute LiveOut(i)
    if LiveOut(i) changed then
      changed ← true

求解方程式。「recompute LiveOut(i)」就是把上一節的方程式右邊代一次，用的是此刻手上的 LiveOut(m)。

  • 只有讀才會進 UEVar，而且要在同一個 block 賦值之前。s ← s + i 裡右邊的 s 進 UEVar，因為掃到它時 s 還不在 VarKill；如果同一個 block 後面還有一條 t ← s + 1，那個 s 就不進了，它讀的是 block 自己算出來的值。運算的順序在這裡有意義，集合本身沒有。
  • 從 ∅ 開始是刻意的。∅ 是「什麼都不活躍」，最樂觀的猜測。重算只會往集合裡加名字，不會拿掉，所以最後停下來的地方是所有解裡最小的那一個。從全集開始也會停，但可能停在一個把多餘名字算成活躍的解，下一節證明。
  • 同一圈裡前面算過的 block 已經是新值。照編號 0 到 N − 1 走，重算 LiveOut(i) 時，編號比 i 小的後繼在這一圈已經更新過，編號比 i 大的還是上一圈的值。這就是為什麼走訪順序會影響圈數。
  • changed 只在集合真的變大時設 true。停下來的條件是「整整一圈沒有任何改變」，所以至少跑兩圈：一圈算出答案，一圈確認它不再變。書上的例子要三圈。

為什麼一定會停，而且停在同一個答案

    
每次重算只做聯集和交集，用到的 UEVar 和 VarKill 整個過程都不變。所以只要右邊用到的 LiveOut(m) 都只變大或不變，左邊算出來的 LiveOut(n) 也只會變大或不變；從 ∅ 開始，歸納下去，每個集合都單調遞增。它們又都是「程式裡出現過的變數名」這個有限集合的子集，不能無限長大。每一圈要不是至少多一個名字進某個集合，就是什麼都沒變而停下，所以圈數有上界，演算法一定終止。這是書上給的論證。

    
走訪順序會改變圈數，但不會改變答案。書上的例子照 B0 到 B4 走要三圈，因為算 B0 的時候 B1 還是 ∅，s 要等第二圈才傳到；改成先算出口再往回（B4、B3、B2、B1、B0）兩圈就停。這個順序是反向 CFG 的 reverse postorder，第九章 9.2 節講 backward 問題該用它。範例「直線程式，照執行順序列」和「同一段程式，倒過來列」是同一段程式的兩種順序，一個五圈、一個兩圈。答案不變的理由比終止多一步，摺疊在下面。

    

      證明：從 ∅ 開始迭代，不管順序，都停在方程組最小的解
      
設 S 是方程組的任何一個解（每個 block 一個集合，同時滿足所有方程式），X 是演算法某一刻手上的集合。

      
    
        
  1. 單調。方程式右邊只有聯集、交集和不變的集合，所以如果每個 LiveOut(m) 都換成包含它的集合，算出來的 LiveOut(n) 也只會包含原來的。
    2. 
        
  2. X 永遠不超過 S。一開始 X 全是 ∅，當然在 S 裡面。重算某個 block 時，新值是用 X 的分量代進右邊算的；X ⊆ S 加上單調，新值 ⊆ 用 S 代進去的值，而 S 是解，代進去正好等於 S 的那個分量。所以重算之後還是 X ⊆ S。這一步沒有用到是哪個 block、什麼順序。
    3. 
        
  3. 停下來的 X 自己是解。最後一圈每個 block 都重算過而且沒有改變，表示每一條方程式代入 X 都成立。
    4. 
      

      
由 2 和 3，X 是解而且包含在每一個解裡，它是最小的解；最小的解只有一個，所以任何順序都停在同一個 X。書上說「迭代資料流分析理論保證該方程組只有唯一解」指的就是這個最小解。方程組本身可以有不只一個解。如果某個變數 v 在迴圈 B1、B3 裡既沒被讀也沒被賦值，「v 在 B1 和 B3 出口都活躍」也同時滿足兩條方程式，只是沒有任何路徑支持它。從 ∅ 開始正是為了不把這種名字放進來；從全集開始會停在最大的解，就會把它算成活躍。

    

    
8.6 節末的復習題問一個反過來的問題：有時候編譯器要的不是「某一條路徑會讀」，而是「離開 b 之後每一條路徑都會在賦值前讀到」。方程式的形狀一樣，只是後繼之間的聯集換成交集；出口 block 沒有後繼，交集的「空」是全集，所以要另外規定它是 ∅，而且初始值要改成全集、讓集合單調遞減，停下來的是最大的解。同一套單調和有限的論證仍然成立，只是方向相反。

  


  

    
用 LiveOut 找沒初始化的變數

    
假設有一個虛擬的入口節點 n0，它有邊連到每一個真正的入口 block。在 n0 出口活躍的變數，就是從程式開頭出發有某條路徑在賦值之前就讀到它的變數，也就是可能沒初始化就被使用的那些。書上的例子只有 B0 一個入口，所以：

    
\[ \mathrm{LiveOut}(n_0) = \mathrm{UEVar}(B_0) \cup \big( \mathrm{LiveOut}(B_0) \cap \overline{\mathrm{VarKill}(B_0)} \big) = \{ s \} \]

    
沿著 ⟨B0, B1, B3⟩ 走，s ← s + i 讀了還沒有被賦值的 s。workbench 跑到最後一步會算這個集合；範例「把 s 的初始化搬到 B0」讓 s 在入口就被賦值，LiveOut(n0) 就變成 ∅。

    
這個方法抓到的是「可能」，不是「一定」，所以可能誤報。分析看不出分支條件之間的關聯，一條實際上走不到的路徑在它眼裡照樣算數；透過指標、陣列元素或呼叫別的程序做的初始化，這一頁的模型完全看不到；在沒有被呼叫者資訊的時候，呼叫點必須假設每個可能被改的變數都被改、每個可能被讀的變數都被讀，這是安全的最壞假設，但會讓集合變大。所以編譯器回報的是警告，不是錯誤。

  


  

    
結語

    
全局分析不模擬執行，而是對每個 block 列一條方程式再解出不動點。活躍變數要三個集合：UEVar 和 VarKill 掃一次 block 就有，LiveOut 由後繼決定，有迴圈時方程式互相依賴，只能從 ∅ 開始反覆代入。重算只做聯集和交集，集合只會長大又有上界，所以一定停；停下來的是最小的解，任何走訪順序都到同一個地方，順序只決定要幾圈。入口的 LiveOut 就是可能沒初始化就被讀的變數。

    
書上第九章把這套做法推廣成一般的迭代資料流框架：換一組集合和一條方程式就是可用運算式、可達定義這些問題，反向 CFG 的 reverse postorder 和 worklist 是讓它跑快的兩個工具，dominator 也是用同一種迭代算出來的。LiveOut 之後會在 SSA 建構（只替活躍的變數放 φ）和 13.4 節的全局暫存器分配裡再出現。這一頁建立在 CFG 的節點和邊上，接在 SVN 停下來的地方；同一節的下一個小節是程式碼放置，用的不是資料流分析而是 profile。

    
這裡的「變數」是程式裡出現過的名字這個隱含的集合，書上提到暫存器分配時會改成對一組精心切出來的 live range 算同樣的方程式。陣列、指標、程序呼叫都不在這一頁的模型裡，多個入口的 CFG 也只有講法沒有範例。
