過程放置：在 call graph 上縮邊

上一頁把一個過程裡的 block 排成一列，讓最常走的邊變成 fall-through。同樣的問題放大到整個程式：可執行檔裡的過程也要排成一列，誰放在誰旁邊是編譯器和 linker 可以選的。call 和 return 永遠是跳躍，這一層省不了跳躍；省的是 cache 和分頁：常常互相呼叫的過程如果放在一起，會落在同一批 cache line、同一頁，指令 cache 的衝突和 page fault 都變少。Engineering a Compiler 8.7.2 的做法是在 call graph 上貪婪地縮邊：每次挑呼叫次數最多的邊 (x, y)，把 y 整個併進 x，直到圖縮成一個節點，合併的順序就是過程的順序。這一頁照圖 8-22 的虛擬碼一步步跑，可以自己改呼叫邊和次數。

過程放在一起省的是什麼

書上的原理只有一句：如果過程 p 呼叫 q，而且編譯器把它們放在記憶體裡相鄰的位置，那麼只要 size(p) + size(q) 不超過指令 cache 的大小，它們就不會在 cache 裡互相衝突。相鄰也提高了 p 和 q 落在同一個虛擬記憶體分頁的機會，working set 變小，page fault 變少。所以目標是：讓「caller 和 callee 放在相鄰位置」的呼叫次數最多。書上補了一句：虛擬位址到實體位址的對應會讓「相鄰就不衝突」沒那麼絕對，但 cache 的關聯度（associativity）應該可以緩解。

這個目標不可能全部滿足。call graph 的每條邊 (p, q) 都是一個「p 和 q 應該相鄰」的要求；p 呼叫了 q、r、s 三個過程，它們不可能全都放在 p 旁邊。所以過程放置用貪婪近似找一個夠好的佈局，不去算最好的。

跟 block 的放置一樣，演算法要的是每條邊的執行次數，可以來自 profile 也可以是估計。不一樣的是它要看到整個程式的 call graph，分開編譯時單一個編譯單位看不到，所以這件事通常在 link time 或是 whole-program 的模式下做。

縮邊：把 y 併進 x

演算法分析的對象是 call multi-graph：p 裡有三個地方呼叫 q 就有三條 (p, q) 的邊。初始化時先把這種平行邊合併成一條，權重相加；過程呼叫自己的 self loop 直接刪掉，因為一個過程本來就和自己相鄰，怎麼放都影響不了它。每個節點 x 帶一個 list(x)，開始時只有 {x}，記的是「這個節點代表的那群過程，照什麼順序放」。所有的邊照權重從高到低放進一個 priority queue Q。

主迴圈每一輪取出 Q 最前面的邊 (x, y)，然後把 y 塌縮進 x：y 出去的每條邊 (y, z) 改成 (x, z)，y 進來的每條邊 (z, y) 改成 (z, x)；改出來的邊如果 Q 裡已經有一條一樣的，兩條合併、權重相加，Q 重新排序。接著把 list(y) 接到 list(x) 後面，所以 y 那群過程會緊跟在 x 那群後面；最後把 y 和它的邊從圖上刪掉。這一輪之後 x 代表的是一群過程，x 進出的邊是這一群和其他節點之間呼叫次數的總和。這就是合併權重的意義：一群過程和某個節點的來往加起來，可能比任何一條單獨的邊都大，排到 Q 的前面去。圖 8-23 的畫面 4 就是這種情況，(P0, P5) 只有 2，併進 (P0, P1) 之後變成 12，排到了 (P1, P3) 的前面。

Q 空了演算法就停。每合併一次圖少一個節點，所以最後剩下的每個節點對應原始 call graph 的一個連通分量：從入口出發能到達所有過程，就只剩一個節點，它的 list 就是全部過程的全序；有些過程沒有人呼叫，或是呼叫走的是 function pointer 這種看不出目標的路，就會剩好幾個節點、好幾個 list，每個 list 內部的順序還是確定的，list 之間怎麼排演算法沒有規定。

虛擬碼

書上只給分析階段的演算法；變換階段就是照 list 把過程的程式碼重新排一遍，沒有虛擬碼。中譯本的虛擬碼是圖 8-22，例子和每一輪的狀態是圖 8-23，書上叫每一輪的狀態「畫面」，這一頁沿用。

// Initialization work
build the call multi-graph G
initialize Q as a priority queue           // Order Q highest to lowest
for each edge (x,y) ∈ G do                 // Add weights to the edges
  if (x = y) then
    delete (x,y) from G                    // Self loop is irrelevant
  else
    weight((x,y)) ← estimated execution frequency for (x,y)
for each node x ∈ G do
  list(x) ← {x}                            // Initialize placement lists
  if multiple edges exist from x to y then
    combine them and their weights
  for each edge (x,z) ∈ G do               // Put each edge into Q
    Enqueue(Q, (x,z), weight((x,z)))

// Iterative reduction of the graph
while Q is not empty do
  (x,y) ← Dequeue(Q)                       // Take highest priority edge
  for each edge (y,z) ∈ G do               // Move source from y to x
    ReSource((y,z), x)
  for each edge (z,y) ∈ G do               // Move target from y to x
    ReTarget((z,y), x)
  append list(y) to list(x)                // Update the placement list
  delete y and its edges from G            // Clean up G
  • ReSource 和 ReTarget 會合併邊。書上在圖後面說明：ReSource 把 (y, z) 換成 (x, z) 並更新 Q，如果 (x, z) 已經存在，就把兩條的執行次數合併；ReTarget 對 (z, y) 做同樣的事。合併後新邊的權重是兩條舊邊之和。
  • self loop 在兩個地方出現。初始化時遞迴的邊直接刪掉。主迴圈裡如果 y 也呼叫 x，ReSource 會把 (y, x) 改成 (x, x)，也是 self loop；書上沒寫怎麼處理，這一頁照同一個理由丟掉。範例「入口不一定排第一」會碰到。
  • Q 怎麼排，書上沒有全部說明。這一頁照圖 8-23 做：權重相同的邊照輸入列出的順序；改了來源或目標但權重沒變的邊留在原來的位置（畫面 2 的 (P1, P5)）；合併後權重變大的邊往前移到所有權重不小於它的邊後面（畫面 4 的 (P0, P1)）。
  • 最後剩下好幾個 list 時，這一頁把入口所在的 list 放最前面，其他照節點名字排。這是為了給 workbench 一個確定的輸出，不是書上的規則。

和 block 的放置哪裡不同

    
書上說兩者有微妙的不同。全局程式碼放置要讓 hot path 變成 fall-through，fall-through 要求 x 的最後一條指令緊接 y 的第一條，所以建鏈時只有「x 是一條鏈的尾、y 是另一條鏈的頭」的邊才接得上，其他的邊全部忽略。過程放置的目標只是放得近：p 呼叫 q，只要 p 到 q 的距離小於 cache 的大小就達到目的了。所以它可以用上鏈中間的過程之間的邊，自由度大得多：縮邊沒有頭尾的限制，任何一條邊都能縮，而且縮完的圖還在，合併後的權重會繼續影響後面的選擇。

    
自由度的代價是相鄰關係沒那麼準。list(y) 整串接在 list(x) 整串後面，真正碰在一起的是 x 那群的最後一個和 y 那群的第一個，不一定是 x 和 y 本身。書上的例子裡畫面 4 用 (P1, P5) 做合併，但接出來的是 {P1, P2} 加 {P5, P6, P4}，碰在一起的是 P2 和 P5，P1 和 P5 隔了一個位置。對「放得近」來說這沒有關係。Pettis 和 Hansen 1990 年的原始版本在接兩群時會試四種接法（哪一群在前、要不要把一群反過來），挑碰在一起的那一對權重最大的；書上這版省略了。workbench 最後一步算的「每條邊隔多遠」和「相鄰的呼叫次數」是這一頁拿來看結果的方法，不是書上的。

圖縮到最後剩什麼

    
書上在例子結尾提醒：這個例子的佈局從入口 P0 開始，是權重剛好這樣，不是演算法的設計。演算法裡沒有任何一行看入口。一個沒有人呼叫的過程永遠不會當 y，它的 list 永遠以自己開頭；但入口可以當 x 把別人併進來，併進來的過程如果有別人呼叫，ReTarget 就會造出一條指向入口的邊，入口之後就可能被那個呼叫者併走。範例「入口不一定排第一」就是這樣：main 先吃掉 tick 和 draw，on_event 呼叫 tick 的 300 次變成指向 main 的邊，最後 main 整群被併進 on_event，佈局以 on_event 開頭。對 block 的放置來說入口必須排第一，對過程來說沒有這個限制，main 放在哪裡都能跑。

    
範例「不只一個連通分量」裡有兩個 plugin 只透過 function pointer 被呼叫，call graph 上看不到那條邊，還有一個從來沒被呼叫的過程。最後剩三個節點、三個 list。書上說這兩種情況（沒有呼叫的路，或是路被有歧義的呼叫遮住）都會讓圖剩好幾個節點，編譯器和 linker 一樣可以用這些 list 決定相對的順序；list 之間的先後要另外決定。

  


  

    
結語

    
過程放置把整個程式的過程排成一列，目標是讓互相呼叫最多的過程放得近，減少指令 cache 的衝突和 page fault。演算法在 call multi-graph 上貪婪地縮邊：合併平行邊、刪掉 self loop，然後每一輪取權重最高的 (x, y)，把 y 的邊改接到 x、list(y) 接到 list(x) 後面、刪掉 y。合併後的權重是一群過程和外界來往的總和，會改變後面的選擇。Q 空了之後每個剩下的節點對應一個連通分量，它的 list 就是那群過程的順序。和 block 的放置比，它不要求精確相鄰，所以任何邊都能縮，也不在乎入口排在哪裡。

    
這是 8.7 節過程間最佳化的第二個例子，第一個是 inline substitution，第三個小節講編譯器要怎麼組織才能做過程間的分析。第九章接著把 LiveOut 推廣成一般的資料流框架。實務上過程放置在 linker 做，輸入是 profile 的 call graph；現代的做法（像 LLVM 的 lld 和 Meta 的 BOLT）用的還是 Pettis 和 Hansen 這一套的後代，只是把 cache line 和分頁的大小、過程的大小都算進去。

    
這一頁的模型把過程當成沒有大小的點，只看呼叫次數；真的 linker 要看每個過程佔幾個位元組，兩個過程相鄰但加起來超過一頁，相鄰就沒有意義。書上這一節也沒有講 list 之間怎麼排、冷的過程要不要集中搬到一邊，這些都不在 workbench 裡。
