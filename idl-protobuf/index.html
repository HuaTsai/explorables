IDL 與 protobuf 同一筆資料的兩種線上格式

兩個程式要交換一筆資料，可能一個是 C++、一個是 Python，一個跑在 ARM、一個跑在 x86。DDS 的 OMG IDL 和 Google 的 protobuf 用同一招解決：寫一份和語言無關的定義檔，讓工具產生兩邊的程式。差別在線上的 bytes 長什麼樣子。輸入一筆訊息，看兩種格式各編出哪些 byte。

三個零件：定義檔、產生器、線上格式

這類工具都由三個零件組成。定義檔描述資料有哪些欄位、什麼型別；產生器讀定義檔，產生各語言的 struct 和序列化程式；線上格式是序列化之後實際送出去的 bytes。兩邊只要拿同一份定義檔各自產生程式，就能互相讀懂。

零件DDSprotobuf
定義檔OMG IDL（.idl），源自 1991 年的 CORBA.proto
產生器各家 DDS 自帶，例如 Fast DDS 的 fastddsgen、ROS 2 的 rosidlprotoc 加上各語言的 plugin
線上格式CDRprotobuf binary（也可以轉成 JSON 或文字格式）
主要用途DDS 的 publish／subscribe，ROS 2 的底層gRPC、儲存、各種服務之間的 API

ROS 2 是個好例子：使用者寫的是更簡單的 .msg，build 時 rosidl_adapter 先把它轉成標準的 OMG IDL，再交給底下的 DDS 工具產生程式，線上跑的就是 CDR。

兩份定義檔

下面是同一筆「感測器讀值」的兩種寫法，workbench 用的就是這兩份。

OMG IDL

module demo {
  struct Reading {
    uint16          id;
    int32           temperature;  // 單位 0.01 °C
    sequence<int32> samples;
    string          name;
    boolean         valid;
  };
};

protobuf（proto3）


      

    

    
差別一眼就看得出來：protobuf 每個欄位後面有一個編號（= 1、= 2），IDL 沒有。這個編號會寫進線上的 bytes，是兩種格式所有差異的源頭。型別也不完全對得上：protobuf 沒有 16-bit 整數，uint16 只能寫成 uint32；IDL 的固定長度陣列（int32 x[3]）在 protobuf 只能寫成 repeated。有號整數 protobuf 還分 int32 和 sint32 兩種，workbench 裡可以切換。

  


  

    
編碼規則

    

      

        
CDR（XCDR1，little-endian）Fast DDS 2.x 和 ROS 2 Humble 預設用 XCDR1。XCDR2 把最大對齊從 8 bytes 降到 4 bytes，並加上下面「版本演進」提到的長度標頭。

        
    
          
  1. 開頭 4 bytes 是封裝標頭：00 01 代表 little-endian 的 CDR，後面 2 bytes 是 options。
    2. 
          
  2. 照定義檔的順序寫每個欄位，不寫欄位名稱，也不寫編號。
    3. 
          
  3. 每個值先對齊到自己大小的倍數（從標頭之後開始算），空出來的位置是 padding。
    4. 
          
  4. 整數用固定長度：uint16 2 bytes、int32 4 bytes，負數是二補數。
    5. 
          
  5. sequence 和 string 先寫 4 bytes 的長度；string 的長度包含結尾的 \0。
    6. 
        

      

      

        
protobuf（proto3）

        
    
          
  1. 值等於預設值（0、空字串、false、空陣列）的欄位直接不寫。
    2. 
          
  2. 每個欄位先寫一個 key：欄位編號 << 3，低 3 bit 放 wire type。
    3. 
          
  3. 整數用 varint：每 byte 放 7 bit，最高 bit 代表「後面還有」。int32 的負數會被當成 64-bit 處理，一定是 10 bytes；sint32 先做 zigzag 再編。
    4. 
          
  4. string 和 repeated 的數字（proto3 預設 packed）先寫長度，再寫內容。
    5. 
          
  5. 不需要對齊，沒有 padding。
    6.

為什麼差這麼多：設計目標不同

    
CDR 追求「讀起來快」。欄位照順序、每個值對齊好，接收端幾乎可以直接照固定的位置讀，整數不用解碼。代價是兩邊的定義必須完全一樣：線上沒有欄位名稱也沒有編號，接收端完全照自己手上的定義去讀。發送端多加了一個欄位、接收端還是舊版，後面的欄位就全部錯位。輕則讀到錯的數字，重則整筆解不開被丟掉，而且畫面上通常看不出原因。

    
protobuf 追求「體積小」和「兩邊版本不同也能溝通」。每個欄位自帶編號和 wire type，所以：

    
    
      
  • 舊版程式收到新版多出來的欄位，看 wire type 就知道要跳過幾個 byte，直接略過；
    • 
      
  • 新版程式收到舊版缺少的欄位，就當成預設值；
    • 
      
  • 欄位改名字沒關係，因為名字不在線上；但編號一旦用過就不能改，也不能拿給別的欄位用。
    • 
    

    
代價是接收端一定要逐個 byte 解析，varint 也要拼回整數，沒辦法直接照位置讀。另外，因為預設值不送，proto3 分不出「沒給」和「給了 0」proto3 從 3.15 版起可以在欄位前加 optional，那個欄位就會記錄「有沒有給」，即使值是 0 也會送出。。

    
DDS 也意識到這個問題。DDS-XTypes 規格讓 struct 可以加上註記：@final 就是上面的樣子；@appendable 在 struct 前面加 4 bytes 的總長度，允許在最後面加欄位；@mutable 讓每個欄位都帶 ID 和長度，可以任意增刪，效果就跟 protobuf 很像了。換句話說，兩邊其實是在「速度」和「可演進性」之間選了不同的預設值。

  


  

    
其他類似的東西

    
「定義檔加產生器加線上格式」這個組合很常見。差別主要在兩件事：線上帶不帶欄位編號，以及接收端能不能不解碼就直接讀。

  


  

    

      
名稱定義檔線上格式的特色常見用途

      
        
ROS 2 .msg.msg自己不定義格式，先轉成 OMG IDL，線上是底層 DDS 的 CDR機器人

        
Apache Thrift.thrift和 protobuf 很像：欄位帶編號；另外附整套 RPC 框架服務之間的 RPC

        
Apache AvroJSON 寫的 schema線上什麼標記都不帶，最精簡；接收端必須拿到寫入端用的 schema 才能解Kafka、Hadoop 的資料儲存

        
FlatBuffers.fbs不用解碼：靠 offset 表直接在 buffer 裡找欄位，可以只讀其中一個欄位遊戲、TensorFlow Lite 模型檔

        
Cap'n Proto.capnp線上格式就是記憶體裡的格式，以 8 bytes 為單位排好，收到就能用低延遲 RPC

        
ASN.1ASN.1 語法同一份定義有多種編碼：BER、DER 帶型別和長度；PER、UPER 擠到 bit 級別X.509 憑證、4G／5G 信令、車聯網 V2X

        
SOME/IPARXML 或 Franca IDL和 CDR 類似，欄位照順序、固定長度，預設 big-endianAUTOSAR 車用服務導向通訊

        
MessagePack、CBOR不需要二進位版的 JSON：每個值自帶型別，沒有 schema 也能解取代 JSON 的場合

      
    

  


  

    
那要怎麼選：通常是生態系先決定

    
上面列了一堆差異，但實務上很少有人單獨挑編碼格式。編碼通常是跟著通訊框架一起來的：用 DDS 就是 CDR，用 gRPC 就是 protobuf，Kafka 常搭 Avro 或 protobuf，AUTOSAR Classic 就是 SOME/IP，瀏覽器就是 JSON。真正在比較的是通訊模型（publish／subscribe 加上 QoS 和自動探索、request／reply 的 RPC，還是可以重播的資料流），以及上游已經綁定了什麼。例如用了 ROS 2，底層就是 DDS，CDR 是跟著來的，沒有選的空間。

    
workbench 裡最顯眼的「誰比較小」，通常最不重要。一筆 DDS 資料在網路上，光 RTPS 的標頭就有 20 bytes，DATA 子訊息的標頭再 24 bytes，加上 UDP 和 IPv4 的 28 bytes 與乙太網路的標頭。小訊息省下的十幾個 byte 被這些固定開銷蓋過；大訊息（影像、點雲）則幾乎全是資料本身，這時候真正影響效能的是資料被複製了幾次（共享記憶體、zero-copy），不是編碼省了幾個 byte。gRPC 也一樣，HTTP/2 有自己的 frame 標頭。

    
格式本身的特色只在下面幾種情況會變成決定性的：

  


  

    

      
情況為什麼格式會有差傾向

      
        
兩邊會各自更新版本資料存很久，或各元件分開更新、現場同時有新舊版本。欄位沒有編號的格式，一邊改了就讀錯protobuf、Thrift，或 DDS 的 @appendable／@mutable

        
頻寬極小或按量計費CAN、行動網路、衛星，每個 byte 都有成本protobuf、ASN.1 UPER

        
功能安全、要可預測固定長度、能事先算出最大大小，記憶體可以預先配置SOME/IP、有長度上限的 CDR

        
大陣列、低延遲不想逐個欄位解碼，希望直接在 buffer 裡讀FlatBuffers、Cap'n Proto，或 DDS 的共享記憶體

        
要給人看、好除錯肉眼可讀，工具最多JSON

      
    

  


  

    
所以比較實際的順序是：先看通訊模型和上游綁定了什麼；再問兩邊會不會各自演進，這是格式特色裡影響最大的一項；效能放最後，而且要實際量過才算數。如果被綁在一個生態系裡，但又需要演進能力，也有折衷做法：在 DDS 的訊息裡放一個 sequence<octet> 欄位，裡面裝 protobuf 編好的 bytes。傳輸用 DDS 的 QoS 和自動探索，演進靠 protobuf 的欄位編號。代價是 DDS 的工具看不到裡面的欄位。

  


  

    
結語

    
IDL 和 protobuf 的相同之處是「一份定義檔，產生各語言的程式」；不同之處在線上格式的取捨。CDR 不帶欄位編號、固定長度、照順序對齊，讀得快，但兩邊的定義必須一模一樣；protobuf 每個欄位自帶編號，用 varint 壓縮整數、預設值不送，體積小，而且兩邊版本不同也能溝通，代價是一定要逐個 byte 解析。用 DDS 時，兩邊的定義檔要當成同一份來源來管理，改了一邊就要同時重新產生另一邊；不然就是用 XTypes 的 @appendable、@mutable 換取演進的空間。選型時，格式特色通常排在通訊模型和上游生態系之後；其中真正會左右決定的，是兩邊會不會各自演進，而不是誰少幾個 byte。

    
這一頁的 CDR 只示範了 XCDR1 的 @final struct，沒有畫 XCDR2 的長度標頭、union、巢狀 struct、key 欄位。protobuf 也只用了 proto3 最基本的型別，沒有談巢狀 message、oneof、map 和 fixed 系列的整數。
