micro-op 複雜指令進了核心變成什麼

現代 CPU 核心不直接執行你看到的指令。前端把每一條翻成一到數個 micro-op，後端只看 micro-op。按「下一步」把同一段 C 的三種機器碼一條一條送進前端，看每條被拆成幾個、拆成什麼。

指令是契約，µop 是實作

x86 的 inc qword ptr [rdi + rsi*8] 一條指令要讀記憶體、加一、再寫回去。核心裡沒有一個單元能一口氣做完這三件事，所以前端的解碼器把它拆成幾個簡單操作：讀取、ALU、寫入。這些簡單操作就是 micro-op（µop），長得很像 RISC 指令。後端的排程器、執行單元、重排序緩衝只認得 µop，不知道原本的指令長什麼樣。

AArch64 和 RISC-V 的指令本來就接近 µop，但也不是一對一。AArch64 的 stp x30, x19, [sp, #-16]! 存兩個暫存器還順便更新 sp，在 Apple M1 上拆成 3 個 µop。反過來，x86 和 ARM 的核心都會把「比較 + 條件跳轉」兩條指令合併成一個 µop（macro-fusion）。拆和合在三邊都會發生。

重點是：µop 數是微架構的屬性，不是 ISA 的屬性。同一條 x86 指令在 Intel Skylake 和 AMD Zen 4 上拆法不同，同一條 AArch64 指令在 Apple M1 和 ARM Neoverse V2 上也不同。所以下面每條帶子都標明 CPU 模型，可以切換。數字來自 llvm-mca（LLVM 23）的排程模型，它是 LLVM 為了做指令排程而維護的近似，不是晶片廠的官方數據；RISC-V 用 SiFive P550 的模型，因為它是 llvm-mca 裡少數有亂序核心模型的 RISC-V 核心。

結語

    
ISA 是契約，µop 是實作，CISC 的複雜度被前端吸收掉了：x86 一條讀改寫指令進了核心，後端看到的和 RISC-V 的四條指令幾乎一樣，所以「x86 跑得慢」這個直覺不成立，執行階段大家做的事差不多。但吸收不是免費的，x86 的解碼器要處理變長指令、前綴、ModRM，面積和功耗明顯大於 ARM 的解碼器，Intel 和 AMD 的回答是 µop cache，解過一次的 µop 存起來，迴圈裡的指令不再經過解碼器。RISC 也會拆、也會合：AArch64 帶 pre-index 的 stp 拆成 3 個，Apple M1 把帶縮放的定址拆成 2 個，cmp 加分支在 x86 和 ARM 上都會合併成 1 個。「指令數等於 µop 數」在三邊都不成立。

    
這一篇是系列的最後一頁，前面幾篇在這裡匯合：解碼器為什麼難，回頭看指令編碼；會被拆開的讀改寫和帶縮放的 load 來自定址模式；會被合併的 cmp 加跳轉來自條件分支。想往下看 µop 進了後端之後的事，llvm-mca 的 timeline view 和 uops.info 的實測表是兩個好起點。

    
這裡的數字來自 llvm-mca 的排程模型，不是晶片廠公布的拆法，有幾個地方要打折：

    
    
      
  • µop 的類型是依指令語意標的。llvm-mca 只給每條指令的 µop 數量，LOAD、ST-ADDR、ALU 這些標籤是合理的推斷。
    • 
      
  • macro-fusion 沒有反映在數字裡。Intel 從 Core 2、AMD 從 Zen、Apple 從 A 系列起都會把 cmp 加條件跳轉合成 1 個 µop，所以 if (a < b) 案例裡 x86 和 ARM 各多算了 1。
    • 
      
  • Intel 的融合域與未融合域。Skylake 的 inc [mem] 實際是 4 個未融合 µop，前端融合後在 µop cache 和重排序緩衝裡算 2 個，llvm-mca 給 3，介於兩者之間。要精確數字請查 uops.info。
    • 
      
  • µop cache 與 loop stream detector。這裡每條指令都經過解碼器，真實核心在迴圈裡大部分時間從 µop cache 取指，x86 的解碼劣勢在那時候不存在。
    • 
      
  • 排程 port 與延遲。µop 進了佇列之後要分配到哪個執行單元、等多少 cycle，這一頁不講。
    • 
      
  • RISC-V 高效能核心的公開資料很少。P550 模型裡每條指令都是 1 個 µop、store 不拆，反映的是 SiFive 沒有公開細節，不代表硬體真的這樣做。
