函式呼叫 參數、回傳位址與堆疊

C 裡一行 inner(a, b)，到了機器碼是一串搬運：參數放進哪個暫存器、回傳位址存在哪裡、哪些暫存器得先備份。按「下一步」看同一個函式在三個 ISA 上每一條指令對暫存器和堆疊做了什麼。

慣例是契約，不是指令集

呼叫慣例（calling convention）規定呼叫者和被呼叫者怎麼交接：參數放哪、回傳值放哪、哪些暫存器被呼叫者可以隨便改（caller-saved）、哪些改了要還原（callee-saved）。這是 ABI（應用程式二進位介面）的一部分，由作業系統和工具鏈決定，不是 ISA 規格的一部分。同一個 x86-64，Linux 和 Windows 就用不同的慣例。

但 ISA 的設計決定了慣例能長什麼樣。最大的分水嶺是呼叫指令怎麼處理回傳位址：x86 的 call 直接把回傳位址壓進堆疊；AArch64 的 bl 和 RISC-V 的 jal 把它寫進一個暫存器（link register），不碰記憶體。葉函式（不再呼叫別人的函式）因此可以完全不碰堆疊；但只要再往下呼叫，這個暫存器就會被覆寫，得先自己存起來。

結語

    
Link register 省下的是記憶體存取，但只有葉函式享受得到：AArch64 和 RISC-V 的 bl 與 jal 不碰堆疊，不再往下呼叫的函式連 sp 都不用動，一旦要往下呼叫，x30 或 ra 得先存進堆疊，和 x86 的 call 與 ret 隱含的壓彈是一樣的量。參數暫存器多就少碰堆疊：x86-64 給 6 個，AArch64 和 RISC-V 給 8 個，callee-saved 的 6 對 10 對 12 也是同一回事。最後，慣例是軟體契約，Windows x64 的參數暫存器只有 rcx rdx r8 r9 4 個，還要留 32 bytes 的 shadow space，同一顆 x86 機器上 Linux 編的函式和 Windows 編的不能直接互相呼叫。

    
慣例裡「哪些暫存器跨 call 要保留」這條規則對程式碼的影響，暫存器那一篇用一個有 N 個存活值的函式量給你看。呼叫和返回指令本身怎麼編碼、跳轉位移放得下多遠，在指令編碼和條件分支。想看 x86 上堆疊和回傳位址更細的動作，首頁的「函式呼叫與 Stack」那一頁用真實位址一步步走。

    
這一頁只傳整數參數、只看 Linux 上的慣例，省掉的規則不少：

    
    
      
  • 浮點參數另有一組暫存器：x86-64 用 xmm0 到 xmm7，AArch64 用 v0 到 v7，RISC-V 用 fa0 到 fa7，整數和浮點各算各的。
    • 
      
  • struct 怎麼傳：小的拆進暫存器，大的用記憶體；回傳大 struct 時呼叫者先配好空間、把指標當隱藏參數傳進去（sret）。三邊的門檻和拆法都不同。
    • 
      
  • 可變參數函式有額外規則，例如 x86-64 要在 al 放浮點參數的個數，RISC-V 的 varargs 一律照 8 bytes 對齊。
    • 
      
  • x86-64 的 red zone：葉函式可以直接用 rsp 以下 128 bytes 而不調 rsp，所以某些葉函式看起來沒開框架卻用了堆疊。
    • 
      
  • AArch64 的保留暫存器：x8 是間接結果位址，x16 和 x17 給連結器 veneer 用，x18 平台保留，x29 慣例上是 frame pointer。範例用 -fomit-frame-pointer，所以沒看到 x29。
    • 
      
  • RISC-V 有好幾套 ABI。這裡是 lp64d；32 位元的 ilp32 系列、沒有浮點硬體的 lp64 變體，傳浮點參數的方式各不相同。Windows x64 整套不同，上面只提了一句。
