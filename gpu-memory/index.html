GPU 記憶體階層逐步圖解

GPU 很快，但它的資料大多放在晶片外面。按「下一步」看一個 warp 的每一條指令往晶片哪裡跑、在哪一層拿到資料、停了多少 cycle。

先認識這顆晶片

下面兩張圖是 NVIDIA H100（SXM5 版）。第一張是整個封裝：中間那塊是 GPU 的 die，兩側的 HBM3 是記憶體，它們坐在同一片基板上，但是不同的晶片。你在 CUDA 裡 cudaMalloc 拿到的 global memory 就在 HBM 裡，也就是在 GPU 晶片之外。H200 用的是同一顆 die，只把記憶體換成六顆 HBM3e，圖上可以切換。

die 裡面排滿了小格子，每一格是一個 SM，H100 啟用了 132 個。中間那條是 L2 cache，所有 SM 共用，所有去 HBM 的存取都經過它。第二張圖把一個 SM 放大：它裡面有四個 Processing Block，每個有自己的 warp scheduler、register file 和一排運算單元；底部那塊 256 KB 的 SRAM 同時當 L1 cache 和 shared memory，比例可以設定。旁邊的 TMA 是 Hopper 新加的搬運單元，後面會提到。

程式這邊的名詞對過去是這樣：一個 thread 執行你寫的 kernel 函式；32 個 thread 綁成一個 warp，硬體一次對整個 warp 發一條指令；若干 warp 組成一個 block，整個 block 住在同一個 SM 上，所以 block 內的 thread 才能共用 shared memory。thread 自己的變數放在 Processing Block 的 register file；其他東西都在 HBM，靠 L2 和 L1 快取。

讀取資料的代價差距很大。下表的延遲來自 Hopper 的 microbenchmark 論文，是量級，實際值隨存取樣式和落在哪個 L2 partition 浮動，看倍數就好。數字取自 Luo 等人 2024 年的 Hopper microbenchmark（arXiv 2402.13499，Table IV）和 2025 年的後續量測（arXiv 2501.12084，Table 3 和 4），都在 H800 PCIe 上量，和 H100 是同一顆 die。模擬器把它們取整成 shared 30、L1 40、L2 260、HBM 600 cycle。

    對照：CUDA 裡的關鍵字各自住在哪裡
    
    
    上面的 kernel 只用到 register、shared 和 global。CUDA 還讓你指定其他幾種放法，下表對回兩張圖上的位置。「本體」是資料真正存放的地方，「路徑」是讀取時經過哪些快取。Register、shared、constant cache、L1、TMA 都在第二張圖的 SM 裡；L2 在第一張圖 die 中央；其餘本體都在第一張圖的 HBM，或根本在這張圖之外的主機記憶體。
    
  
    
  
    
    
    
      
    你在程式裡寫的本體在哪讀取路徑誰看得到 / 活多久你能控制什麼
    
      
        
    int i; float s;kernel 內的純量變數Processing Block 的 register file不經任何 cache單一 thread，kernel 執行期間compiler 決定用幾個。__launch_bounds__ 或 -maxrregcount 設上限，超過就 spill 到 local memory
    
        
    Local memory動態索引的陣列、register spillHBM 裡每個 thread 自己的一小塊L1 → L2 → HBM，與 global 相同單一 thread，kernel 執行期間看 -Xptxas -v 的 spill 數；改用常數索引或減少 register 壓力來避免
    
        
    __shared__SM 內那塊 256 KB SRAM直接讀，不會 miss同一個 block，block 結束就消失；Hopper 起可透過 cluster 讀鄰近 SM 的 shared（distributed shared memory）靜態宣告大小，或 extern __shared__ 加 launch 第三個參數；cudaFuncSetAttribute 的 carveout 調 L1 / shared 比例；__cluster_dims__ 宣告 cluster

    從 H100 到 GB300：又多了什麼
    
      
    H100 之後兩代是 Blackwell（B200）和 Blackwell Ultra（B300）；GB300 是把兩顆 B300 和一顆 Grace CPU 放在同一塊板上的 superchip。NVIDIA 沒有為這兩代出像 Hopper 那樣的架構 whitepaper，SM 內部的單元數沒有官方數字，所以下面只畫到封裝這一層，SM 內部用文字講。再往後的 Rubin（2026 年出貨）維持兩顆 die，224 個 SM，八顆 HBM4 共 288 GB、22 TB/s，NVLink-C2C 加到 1.8 TB/s。SM 內部同樣沒有公開圖。每一點後面標的是它改了這頁的哪一條規則。
    
    
    
    
    
      
    
      
    B300 封裝（示意，不按比例）。兩顆 reticle 大小的 die 用 NV-HBI 接成一顆 GPU，L2 各半，八顆 12-Hi HBM3e 全部啟用。B200 用同一對 die，開的 SM 較少、HBM 是 8-Hi。
    
    
    
    
    
      
    
        
    新東西在哪裡改了這頁的哪條規則
    
        
          
    兩顆 die 一顆 GPUB200 / B300 都是兩顆 die 用 NV-HBI（約 10 TB/s）接起來，軟體看到一顆 GPU。L2 共 126 MB，一半在各自的 die 上。「L2 整顆共用、延遲一個值」不再成立。存取對面 die 那半 L2 的延遲和頻寬都比較差（B200 本地 21 TB/s，跨 die 16.8 TB/s）。Hopper 的 L2 已經有近端 / 遠端 partition 之分，雙 die 把這個差距拉大。
    
          
    Tensor Memory（TMEM）每個 SM 多一塊 256 KB，128 lane × 512 column × 32-bit，只給 Tensor Core 用。矩陣乘的累加器放這裡，不再佔 register file。階層表多一層。它像 shared memory 一樣由程式員配置和釋放（tcgen05.alloc），但一般的 FP32 core 不能直接讀，要先搬回 register。
    
          
    HBM3e 八顆全開B300 288 GB，約 8 TB/s；B200 180 GB。沒有關掉的 stack 或結構件。「每個 SM 每 cycle 分到約 13 B」要重算：B300 約 8 TB/s 分給 148 到 160 個 SM，每 cycle 約 25 到 28 B。跨步讀浪費的絕對量變大，但相對比例一樣是 32 倍。
    
          
    GB300：CPU 和 GPU 記憶體合成一個 pool兩顆 B300 加一顆 Grace CPU，之間用 NVLink-C2C（900 GB/s）。Grace 的 LPDDR5X（最多 480 GB）和 GPU 的 HBM 在同一個 cache coherent 位址空間。對照表最後兩列變了：host memory 不再是「每次跨 PCIe、不快取」，GPU 可以直接讀 CPU 的記憶體並快取在 L2，只是頻寬比 HBM 低一個數量級。cudaMallocManaged 的 page fault 搬移也變成硬體 coherence。
    
          
    Cluster 變大、TMA 變強cluster 最多 16 個 block（H100 也是 16，但 portable 上限 8）；Tensor Core 指令可以跨兩個 block 做一個矩陣乘（cta_group::2）。TMA 支援更多 layout。「shared memory 只有同一個 block 看得到」的放寬從 Hopper 開始，Blackwell 讓它成為主要用法：兩個 SM 的 shared memory 合起來餵一個矩陣乘。
    
          
    取捨：FP64 砍、SFU 加B300 把 FP64 吞吐砍到 B200 的約三十分之一（約 1.2 TFLOPS）；SFU 的指數運算加倍到每 SM 每 cycle 32 次。不是記憶體層的變化，但說明 SM 圖右下那排 FP64 core 和 SFU 的比例會隨產品定位改變。B300 是為 attention 的 softmax 調的。
    
            
      
    
    
    
  
    

  
    
    
    結語
    
    
    Shared memory 和 L1 是同一塊 SRAM，差別是誰管：L1 由硬體自動快取，shared 由你自己搬，它不是「比 L1 更快的一層」，而是「保證在這裡、不會被別人擠掉」的一層。一個 warp 發出 load 之後不會停下來，直到有指令要用那個還沒回來的 register 才 stall，所以連續幾個獨立的 load 等待時間會重疊而不是相加。記憶體以 cache line 為單位搬，32 個 thread 讀 32 個相鄰的 float 只動一條 line，讀相隔很遠的要動 32 條，延遲一樣但吃掉 32 倍的頻寬，而 HBM 頻寬分到每個 SM 每 cycle 只有十幾 byte，浪費不起。
    
    
    這一頁只有一個 warp，所以每次等記憶體都是真的在等。真正的 SM 上同時住著幾十個 warp（H100 最多 64 個），一個在等的時候 scheduler 會切去發別的 warp 的指令，這才是 GPU 藏住幾百個 cycle 的主要方法，也是 occupancy 這個指標的來源。另一條線是上面「從 H100 到 GB300」那一節：雙 die 的 L2、TMEM、CPU 和 GPU 共用的位址空間，每一項都在改這一頁的某條規則。
    
    
    模擬器裡的 L1 和 L2 只記「這條 line 在不在」，沒有容量上限也不會被驅逐；真的 L2 以 32 B sector 為單位搬，L1 的 line 是 128 B，這裡統一用 128 B。延遲全部用固定值（shared 30、L1 40、L2 260、HBM 600 cycle），實際上 L2 分兩個 partition，近端命中約 260、遠端約 410，HBM 在 480 到 660 之間，模擬器一律當近端。沒有進模擬器的還有：
    
    
      
      
    • shared memory 的 bank conflict、L1 的寫入策略、TLB、常數記憶體、texture 路徑、TMA 和 distributed shared memory；store 在這裡視為寫穿到 L2 且不讓 warp 等待。
