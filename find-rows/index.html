find_rows 逐步圖解

一個 {key: row} 的 dict 查表，用「排序 + 二分搜尋」寫成沒有迴圈的 tensor 運算。一行 code 一步，每一步把整個中間 tensor 攤開來看：pos 長什麼樣、hit 長什麼樣、最後回傳的又長什麼樣。

問題是什麼

稀疏卷積把每個 active voxel 的座標 (b, z, y, x) 壓成一個整數 key，存在 keys[N] 裡。第 i 個 key 就是 feature table 的第 i 個 row。建 rulebook 時，對每個 voxel 的每個鄰居座標算出 key，問：「這個鄰居是 active 的嗎？是的話它在第幾 row？」

單筆查詢就是 Python 的 table.get(q, -1)。但一次要查幾百萬筆，而且在 GPU 上，所以要寫成不帶 Python 迴圈的 tensor 運算：每一行 code 對整個 queries tensor 做一次，中間值都跟 queries 同形狀。這裡 queries 故意用二維 [Q, K]，對應「Q 個 voxel 各有 K 個鄰居」，看形狀怎麼一路保留到回傳值。

KEYS原始順序，row 就是 feature table 的列號
QUERIES輸入，不會變
SORTED_KEYS每格掛著原本的 row，底下是落在這格的 query 數
POSsearchsorted 插入點，clamp 後
HITsorted_keys[pos] == queries
RETURNtorch.where(hit, order[pos], -1)

為什麼要先排序

    
searchsorted 是二分搜尋，前提是序列已排序，但 keys 的順序是 feature table 的 row 順序，不能動。所以用 argsort 拿到一個排列 order：order[i] 是「排序後第 i 格原本是第幾 row」。排序後的 tape 每一格都掛著自己原本的 row 號，找到位置之後查回去就行，這就是最後 order[pos] 那一下。

    
排序只做一次，之後 27 個 kernel tap 的鄰居查詢都對同一份 sorted_keys 做。3×3×3 的 kernel 有 27 個位置，每個位置對每個 voxel 查一次鄰居，所以查詢數是 voxel 數的 27 倍。這是 linearize 和 find_rows 拆成兩個函式的原因：key 算一次，查很多次。

  


  

    
clamp 為什麼不會製造假命中

    
searchsorted 回傳的是「插入點」：第一個 ≥ q 的位置。如果 q 比所有 key 都大，插入點是 N，而 sorted_keys[N] 越界，直接索引會炸。

    
於是把 pos clamp 到 N - 1。這看起來像在亂改答案，但接下來要比的是 sorted_keys[N - 1] == q，也就是跟最大的 key 比。q 之所以會落到 N，正是因為它嚴格大於所有 key，包括最大那個，所以這個比較必定是 False。clamp 只是讓越界的 query 走到一個保證 miss 的格子，不會把它變成命中。試試上面「全部越界」的範例，在 clamp 那一步看哪幾格被改動，再看下一步 hit 那幾格全是 False。

    
反過來，小於所有 key 的 query 落在 pos = 0，不越界，直接跟最小 key 比，也是 miss。所以只需要 clamp 上界。

  


  

    
兩個容易漏掉的細節

    
dtype。argsort 和 searchsorted 一律回 int64，不看輸入是什麼。torch.searchsorted 有 out_int32=True 可以直接要 int32，argsort 沒有，所以這裡統一在 order 轉一次。rulebook 全程 int32，所以 order 建立時就轉成 int32，之後 order[pos] 和 where(..., -1) 都維持 int32。漏掉這一步，錯誤要到 Rulebook.__post_init__ 才會爆。

    
空的 keys。N = 0 時 N - 1 = -1，clamp 和索引都會出錯。整幀點雲被 range 濾光在推論端是真的會發生的事，所以函式開頭直接回全 -1，讓它對空輸入也有定義，上層就不必每一處都防。

  


  

    
這跟 hash table 的關係

    

      

        
sort + searchsorted（L1）

        
建表 O(N log N)，每筆查詢 O(log N)。沒有碰撞處理、沒有 load factor、沒有 sentinel key，正確性可以一眼看完。

      

      

        
GPU hash table（L2）

        
建表 O(N)，每筆查詢期望 O(1)。要處理碰撞、選 empty key、調 capacity。spconv 上游走這條。

      

    

    
兩者的介面完全一樣：find_rows(keys, queries) -> rows。docstring 刻意說「背後用什麼是這個函式的私事」，就是為了之後換成 hash table 時，呼叫端和測試一行都不用改。L1 版本的價值是當 L2 的對拍基準。

  

  

    
結語

    
一個 dict 查表可以寫成沒有迴圈的 tensor 運算：先把 keys 排序並記住排列 order，每筆 query 用 searchsorted 找插入點，比對一次決定命中，再用 order[pos] 查回原本的 row。中間值都和 queries 同形狀，所以二維的 [Q, K] 一路保留到回傳值。Clamp 不會製造假命中，因為被 clamp 的 query 一定嚴格大於最大的 key。

    
同一個介面換成 GPU hash table 就是上一節說的 L2 版本，建表 O(N)、查詢期望 O(1)；這一頁的 L1 版本留著當它的對拍基準。

    
這裡的 keys 假設不重複，重複的 key 只會命中排序後的其中一筆，哪一筆由 argsort 的穩定性決定；searchsorted 本身的 GPU 實作和記憶體存取模式也沒有談，這一頁只看形狀和正確性。
