V4L2 影像格式名稱怎麼讀

接一顆相機到 Linux 板子上，會同時碰到 RAW10、0x2B、SRGGB10_1X10、pRAA、RG10 這一串名字。它們講的是同一份影像，只是分別描述它在線上、在元件之間、在記憶體裡的樣子。選一個格式，看每個 bit 落在哪裡。

同一份影像，三個地方三套名字

Linux 的相機 driver 都掛在 V4L2 底下。以 Raspberry Pi 4 接 Camera Module v2 為例：sensor 把影像沿著 CSI-2 的線送出來，Pi 的接收端 unicam 收下，再用 DMA 寫進記憶體，應用程式從 /dev/video0 拿到 buffer。V4L2 把這條路拆成幾種元件：

  • video device：最後的 /dev/videoN。應用程式在這裡設定記憶體格式、要 buffer、開始串流。
  • subdev：sensor、接收端這種中間元件。每個 subdev 有幾個 pad，pad 和 pad 用 link 接起來。
  • media controller：/dev/mediaN，把整張圖串起來，讓你查每個 pad 的格式。

每一段都要知道資料長什麼樣子，但三個地方在意的事不一樣，所以各有一套名字：

位置名字定義在哪誰設定Camera Module v2 的例子
CSI-2 的線上Data Type（DT），6-bit 數字MIPI CSI-2 規格；Linux 抄在 include/media/mipi-csi2.hsensor driver 寫進暫存器的設定0x2B（RAW10）
subdev 的 pad 之間media bus code，MEDIA_BUS_FMT_*include/uapi/linux/media-bus-format.hmedia-ctl --set-v4l2SRGGB10_1X10
記憶體（/dev/videoN）pixel format，4 個字元的 fourccinclude/uapi/linux/videodev2.hv4l2-ctl --set-fmt-videopRAA 或 RG10

接收端的 driver 裡有一張表把三套名字對起來。upstream 的 unicam driver 裡，RAW10 彩色那一筆是這樣：

{
    .fourcc          = V4L2_PIX_FMT_SRGGB10P,   /* 記憶體：照線上的打包原樣 */
    .unpacked_fourcc = V4L2_PIX_FMT_SRGGB10,    /* 記憶體：解開成 16-bit */
    .code            = MEDIA_BUS_FMT_SRGGB10_1X10,
    .depth           = 10,
    .csi_dt          = MIPI_CSI2_DT_RAW10,
    .unpack          = UNICAM_PUM_UNPACK10,
},

一個 media bus code 對一個 DT，卻可以對兩個 fourcc：硬體可以把線上收到的位元原封不動寫進記憶體（SRGGB10P），也可以順手解開成每個 pixel 16 bit（SRGGB10）。下面三節各講一套名字。

線上：CSI-2 的 Data Type

CSI-2 把影像一行一行切成封包，封包標頭裡有一個 6-bit 的 Data Type，告訴接收端這個封包裝的是什麼。常見的值：

DT名稱意思
0x1EYUV422 8-bitYUV 4:2:2，每個分量 8 bit
0x22RGB565每個 pixel 5 + 6 + 5 bit 的 RGB
0x24RGB888每個 pixel 8 + 8 + 8 bit 的 RGB
0x2ARAW8每個樣本 8 bit
0x2BRAW10每個樣本 10 bit，4 個樣本打包成 5 bytes
0x2CRAW12每個樣本 12 bit，2 個樣本打包成 3 bytes
0x2DRAW14每個樣本 14 bit，4 個樣本打包成 7 bytes

RAW 只說「每個樣本幾 bit、怎麼打包」，不說樣本是什麼顏色。彩色 sensor 的 Bayer 資料和黑白 sensor 的灰階，線上都是 RAW10。顏色怎麼排，線上沒有，接收端要從 sensor driver 回報的 media bus code 知道。sensor 送哪一種 DT，是 driver 寫進 sensor 暫存器的設定決定的；Linux 這一側的格式設定只是告訴接收端「準備收這種」，不會反過來改 sensor 的輸出。CSI-2 也能在同一條線上傳非影像的資料，用的是另外的 DT 和 virtual channel，這頁不談。

RAW10 打包的規則是：每 4 個 pixel 一組，前 4 個 byte 各放一個 pixel 的高 8 bit，第 5 個 byte 收集 4 個 pixel 剩下的低 2 bit，第一個 pixel 放在最低的兩個 bit。RAW12 同理，每 2 個 pixel 一組，第 3 個 byte 的低 4 bit 屬於第一個 pixel、高 4 bit 屬於第二個。這樣排的好處是：只看前面的 byte 就能拿到一張 8-bit 的預覽。

Pad 之間：media bus code

media bus code 描述資料在兩個 pad 之間的匯流排上長什麼樣子，名字照固定的規則組成。kernel 文件把它拆成幾段：分量的順序、每個分量幾 bit、每個 pixel 要在匯流排上傳幾次、匯流排多寬，必要時再加上 padding 位置和 byte 順序。

                │      │      └─── 每個 pixel 傳 1 次
                │      └────────── 每個分量 10 bit
                └───────────────── 分量順序：Bayer，左上 2×2 是 R G / G B

UYVY8_2X8YUV 4:2:2，順序 U Y V Y，每個分量 8 bit；每個 pixel 傳 2 次、每次 8 bit8-bit 平行匯流排的 YUV sensor

「2X8」「1X16」原本描述平行匯流排有幾條線、要幾個 clock。CSI-2 是序列匯流排，kernel 文件規定序列匯流排一律用「一次傳一個樣本」的那個名字，因為序列匯流排上這種格式只有一種傳法。所以 CSI-2 sensor 的 driver 寫 UYVY8_1X16，並不代表真的有 16 條線。

Bayer 的四個字母是左上角 2×2 的顏色排列，四種排法都有自己的 code：

RGGB      GRBG      GBRG      BGGR
R G       G R       G B       B G
G B       B G       R G       G R

排列會跟著翻轉改變。水平翻轉把左右對調，RGGB 變 GRBG；垂直翻轉把上下對調，變 GBRG；兩個都翻變 BGGR。Camera Module v2 的 driver（imx219.c）每種 bit 深度都列了四個 code，開了 hflip 或 vflip 就回報對應的那一個。應用程式的 fourcc 要跟著換（例如 pRAA 換成 pgAA），否則 demosaic 出來的顏色會錯。

記憶體：fourcc

fourcc 是 4 個 ASCII 字元，以 little-endian 存成一個 32-bit 數字：'Y12 ' 是 0x59 0x31 0x32 0x20，當成整數讀是 0x20323159。不滿 4 個字元就補空白，所以 'Y12 ' 最後有一個空格，在指令列要加引號。fourcc 的字母沒有統一的文法，但常見的幾族有規律可循：

族fourcc怎麼讀
Bayer，解開RGGB、RG10、RG128-bit 直接一個 byte；10、12-bit 放進 16-bit 的低位，高位補 0，little-endian
Bayer，打包pRAA、pgAA、pRCC小寫 p 開頭，第二個字是排列（R、g、G、B 對 RGGB、GRBG、GBRG、BGGR），排法和 CSI-2 線上一模一樣AA 對 10 bit、CC 對 12 bit 是從現有名字看出來的規律，kernel 文件沒有寫成規則。
灰階GREY、Y10、Y12、Y16Y 加 bit 數，超過 8 bit 的放進 16-bit 的低位
灰階，打包Y10P、Y12PP 結尾，照 CSI-2 的 RAW10、RAW12 打包
灰階，高位對齊Y01212 bit 放在 16-bit 的高位，低 4 bit 補 0

從 fourcc 算出一張 frame 要幾個 byte

拿到 fourcc 和寬高，buffer 大小照下面四步算。driver 在 VIDIOC_S_FMT 和 VIDIOC_G_FMT 回報的 bytesperline 和 sizeimage 就是這樣來的。應用程式讀 pixel 時要用 bytesperline 跳到下一行，不能拿寬度自己乘。

  1. 查這個 fourcc 每個 pixel 在記憶體裡佔幾個 bit。這是容器的大小，不是 sensor 的有效 bit 數。
  2. 一行至少要 ⌈width × bit ÷ 8⌉ 個 byte。
  3. 接收端的 DMA 要求每一行從對齊的位址開始，所以往上取到對齊值的倍數，得到 bytesperline，多出來的是 padding。upstream 的 unicam 對齊到 32 bytes。
  4. sizeimage = bytesperline × height。NV12 這種有兩個 plane 的格式，每個 plane 各算一次再相加。壓縮格式沒有固定的行，V4L2 規定 bytesperline 填 0，sizeimage 是 driver 給的最壞情況上限。

尺寸和接收端的對齊

選格式時會帶入那個裝置常見的尺寸。Raspberry Pi 的例子預設對齊 32 bytes（upstream unicam 的值），USB 攝影機的 bytesperline 由 driver 直接算，預設不對齊。

    同一個字，不同意思
    
    
    packed 有兩種意思。在 YUV 的脈絡裡，packed 是「所有分量交錯放在同一個 plane」，對比的是 planar（Y、U、V 各一個 plane）和 semi-planar（NV12：Y 一個 plane，U、V 交錯成另一個）。在 RAW 的脈絡裡，packed 是「bit 緊緊擠在一起，不補 0」，對比的是 unpacked（每個 pixel 放進 16-bit）。YUYV 是前一種 packed，pRAA 是後一種。
    
    
    名字裡的數字各算各的。SRGGB10 的 10 是每個 pixel 的 bit 數；UYVY8 的 8 是每個分量的 bit 數，換算下來每個 pixel 是 16 bit；NV12 的 12 是平均每個 pixel 的 bit 數；Y16、Z16 的 16 是容器大小，裡面有效的是幾 bit、數字代表什麼單位，要另外查裝置。
    
    
    同一份線上資料，記憶體可以差 60%。Camera Module v2 送出 RAW10，unicam 可以寫成 pRAA（每個 pixel 10 bit），也可以解開成 RG10（16 bit）。後者好讀，但 3280 × 2464 一張從約 9.7 MiB 變成約 15.4 MiB。解開是接收端硬體在做，sensor 和線上完全不知道。
    
    
    對齊方向會讓數值差 16 倍。Y12 把 12 bit 放在低位，讀出來是 0 到 4095；Y012 放在高位，讀出來是 Y12 的 16 倍。用錯其中一種去讀，整張圖的亮度就差 16 倍，或者高位的雜訊被當成資料。
    
    
    bytesperline 不等於寬度乘 bytes。3280 寬的 pRAA，一行資料 4100 bytes，對齊 32 後 bytesperline 是 4128，每行尾巴有 28 bytes padding。拿 4100 算下一行的位置，每往下一行就多歪 28 bytes，整張圖會斜掉。
    
  
    

  
    
    
    在 Raspberry Pi 上看這三套名字
    
    
    Raspberry Pi OS 平常由 libcamera 自動做完這些設定。想自己看的話，先確定沒有別的程式佔著相機，再用這幾個指令（/dev/media0、/dev/video0 的編號依系統而定）：
    

    # 整張 media graph：每個 pad 目前的 media bus code 和尺寸
media-ctl -d /dev/media0 -p

# video node 支援哪些 fourcc、各種尺寸
v4l2-ctl -d /dev/video0 --list-formats-ext

# 設定記憶體格式再讀回來，看 bytesperline 和 sizeimage
v4l2-ctl -d /dev/video0 --set-fmt-video=width=3280,height=2464,pixelformat=pRAA
v4l2-ctl -d /dev/video0 --get-fmt-video

# 抓一張存檔，用 hexdump 對照上面 workbench 的排法
v4l2-ctl -d /dev/video0 --stream-mmap --stream-count=1 --stream-to=frame.raw
hexdump -C frame.raw | head
    
    
    sensor 輸出 pad 的 media bus code、接收端 pad 的 media bus code、video node 的 fourcc，三者要互相對得上。對不上時，設定指令本身多半照樣成功，要到開始串流時才失敗（VIDIOC_STREAMON 回 EPIPE），因為 kernel 是在那個時候才沿著 link 檢查兩端格式。
    
  
    

  
    
    
    結語
    
    
    一份影像在 Linux 上有三套名字：CSI-2 線上的 DT 只講位元數和打包方式；pad 之間的 media bus code 加上了顏色排列和匯流排形狀；記憶體裡的 fourcc 決定 DMA 怎麼把位元放進 byte。接收端 driver 的格式表把三者對起來，而且同一個 DT 可以對到 packed 和 unpacked 兩種 fourcc。讀資料時永遠用 bytesperline 跳行，用 fourcc 的定義拆 bit。
    
    
    這一頁只用單一 plane 的 API 舉例。V4L2 另外有 _MPLANE 系列，讓 NV12M 這種格式的每個 plane 放在不同的 buffer。這裡也沒有談 Bayer 的 DPCM、A-law 壓縮格式、色彩空間和量化範圍（colorspace、quantization 欄位），以及平行匯流排的同步訊號。
